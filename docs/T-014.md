## 배경 / 요구사항 참조

## 작업 단계
1. exercise_sets(id uuid 클라이언트 생성, session_item_id FK cascade, set_no, set_kind CHECK working/warmup/drop/failed_attempt default working, success bool nullable, weight_kg numeric(6,2), reps, duration_seconds, distance_meters, rounds, side CHECK, is_assisted bool nullable, raw_value_note)
2. RLS: session_items → workout_sessions 조인으로 user_id = auth.uid() 4개 정책
3. 인덱스: (session_item_id, set_no)
4. 미기록은 NULL 허용(0 default 금지)

## 결정 / 주의 사항
- id 는 클라이언트 UUID, 저장은 upsert(on conflict (id)). (session_item_id, set_no) unique 는 **deferrable initially deferred**(보정 141000) — **재번호는 한 번의 bulk upsert(한 문장)로** 보내면 순열 이동 중 중간 23505 없이 통과. PostgREST 한 요청에 DELETE 와 upsert 를 섞을 수는 없으므로 삭제는 별 요청(또는 RPC)로 보내고, 그 다음 bulk upsert 로 재번호한다(T-030/T-033). 진짜 중복(같은 set_no 두 행)은 commit 시 23505 — 응답이 409 가 아닐 수 있으니 클라이언트는 전송 전 set_no 중복을 선검증하고 오류 코드와 무관하게 실패를 노출한다.
- **세트 조회·계산은 항상 세션 deleted_at is null 조인 필수**(세트 → 동작 → 세션 2단). soft delete 된 세션의 100kg 가 PR 로 남지 않게(T-049/T-065/T-108 공통 필터).
- is_assisted NULL = 미기록(보조 없음 취급). PR 그룹은 is true / is not true 두 가지만.
- 성공한 본세트(working & success=true)는 reps/duration/distance/rounds 중 하나가 0 보다 크거나 raw_value_note 가 있어야 저장된다(142000→143000) — reps 0 인 채 저장된 100kg 가 PR 후보가 되는 것을 막되, "횟수 기억 안 남" 메모 세트는 유실하지 않는다. 수량도 메모도 없으면 클라이언트는 success 를 NULL 로 보낸다.
- **재번호 upsert 는 각 행의 기존 값 전체를 함께 재전송**한다. (id, session_item_id, set_no) 만 보내면 CHECK 가 충돌 판정보다 먼저 평가되어 23514 (프로브로 고정).
- 프로브는 rls_probe.sql(공통)과 rls_probe_workout.sql(세션·동작·세트·서버 컨텍스트)로 분리(예산). npm run db:rls 가 둘 다 실행.
- 값이 하나도 없는 세트는 거부, raw_value_note(애매한 값 메모)만 있는 세트는 허용. 미기록은 NULL.
- weight_kg 의 의미는 운동의 weight_basis 를 따른다(added=추가 중량, assisted_minus=보조 감량·계산 제외, T-120).
- 계산(볼륨·PR)은 set_kind=working(+success=true) 만. (working 부분 인덱스는 141000 에서 삭제 — 실제 쿼리가 생길 때 T-123 뷰와 함께 다시 본다.)
- 검증: rls_probe 1(anon 거부에 세트 포함)·7b(타인 세트 조회/수정/삭제 0건, 재번호 upsert, soft delete 제외).
- weight_kg 1000 이상은 check(23514), 10000 이상은 numeric 오버플로(22003) — 클라이언트가 범위를 먼저 검증한다(T-030).

## 쉬운 설명

**한 줄 요약**  
한 운동(예: 데드리프트) 안의 각 세트 정보(세트 번호, 반복 횟수, 중량, 소요 시간 등)를 저장하는 테이블을 만든다.

**왜 필요한가**  
사용자가 "데드리프트 40kg × 10 (1세트), 40kg × 10 (2세트), 50kg × 5 (3세트)"처럼 여러 세트를 기록할 수 있어야 한다. 각 세트의 중량, 반복, 시간, 거리를 개별 저장해야 PR(개인 최고 기록) 계산과 성장 분석이 정확하게 가능해진다(FR-005, FR-006).

**끝나면 보이는 것**
- Supabase 대시보드에 exercise_sets 테이블 생성됨
- 자신의 세션 세트만 조회/저장 가능, 다른 사용자 세트 접근 불가능
- 중량, 반복, 시간, 거리 중 운동 유형에 맞게 선택 입력 가능 (모두 nullable)

**주의**  
선행 작업 T-013(workout_exercises)이 반드시 완료되어야 한다. RLS 정책이 workout_exercise → session → user_id 조인 경로로 검사되므로 복잡한 RLS 정책 작성이 필요하다. 30분 안에 끝내려면 T-013의 테이블 구조를 정확히 이해해야 한다.
